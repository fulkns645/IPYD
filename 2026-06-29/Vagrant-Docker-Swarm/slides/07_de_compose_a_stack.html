Compose vs Stack

docker compose up

Aplicación multi-contenedor

Levanta servicios definidos en un archivo YAML, usualmente en un solo host Docker.

  • Ideal para desarrollo y pruebas locales.
  • Control directo sobre contenedores.
  • No requiere un clúster.
docker stack deploy

Aplicación orquestada

Declara servicios para que Swarm los distribuya, escale y mantenga en un clúster.

  • Trabaja con services, tasks y nodes.
  • Usa redes overlay del clúster.
  • Permite políticas de despliegue.
Aclarar que un archivo parecido puede usarse en ambos escenarios, pero el modelo de ejecución cambia. En Stack, Swarm decide dónde y cómo ejecutar las tareas.

¿Qué es un Stack?

Un stack agrupa los recursos que componen una aplicación desplegada sobre Swarm.

Services

Unidades lógicas escalables.

Networks

Comunicación entre servicios.

Volumes

Persistencia de datos.

Idea clave: un stack permite declarar la aplicación completa, no comandos aislados de servicios.

Enlazar con la definición usada en el material: stack como conjunción de services, volumes y overlay networks. Reforzar que el stack es la unidad lógica de despliegue de una aplicación.

Un archivo Compose para Swarm

version: "3.9"

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    networks:
      - appnet
    deploy:
      replicas: 3
      restart_policy:
        condition: on-failure

networks:
  appnet:
    driver: overlay
  • services: declara los servicios de la aplicación.
  • networks: define una red overlay para comunicación distribuida.
  • deploy: expresa decisiones de orquestación propias de Swarm.
Mostrar que la sección deploy es particularmente importante en Swarm. No detenerse demasiado en todos los atributos posibles; solo explicar réplicas y política de reinicio.

Desplegar el Stack

Comando
docker stack deploy \
  -c compose.yml \
  demo

El nombre demo se convierte en el identificador del stack.

Efecto
  • Swarm lee la especificación.
  • Crea servicios, redes y volúmenes.
  • Programa tasks en los nodos disponibles.
  • Empieza a mantener el estado deseado.
Aclarar que el despliegue no crea “un contenedor llamado web”, sino un servicio dentro del namespace del stack, por ejemplo demo_web.

Inspeccionar el Stack

docker stack ls

docker stack services demo

docker stack ps demo

docker service ls

docker service ps demo_web
stack services
Vista lógica de los servicios del stack.
stack ps
Vista operacional de las tasks y nodos.
Insistir en la lectura de los comandos: stack services responde “qué servicios existen”; stack ps responde “dónde están ejecutándose sus tareas”.

Esta diapositiva busca consolidar el modelo conceptual. El archivo no “ejecuta contenedores”; declara servicios que se convierten en tareas distribuidas.

Diferencias y advertencias

Importante
  • Las imágenes deben estar disponibles para todos los nodos.
  • El stack usa servicios, no contenedores individuales.
  • Los nombres suelen quedar prefijados por el nombre del stack.
  • Las redes overlay son naturales en este contexto.
Cuidado
  • No todo archivo Compose se comporta igual en Swarm.
  • Algunas opciones de Compose local pueden ser ignoradas.
  • Los servicios con estado requieren diseño adicional.
  • Construir imágenes localmente no basta si hay varios nodos.
Advertencia práctica importante: si un servicio usa una imagen construida localmente solo en el manager, un worker no podrá ejecutarla. Se necesita registry o construirla en cada nodo.

Retirar el Stack

docker stack rm demo

docker stack ls

docker service ls

docker network ls

Lectura operacional: eliminar el stack remueve los servicios asociados, pero conviene verificar redes, volúmenes y recursos persistentes.

La eliminación del stack es una buena oportunidad para reforzar higiene operacional. En entornos reales, los volúmenes y datos requieren tratamiento cuidadoso.

Takeaways

  • docker compose up y docker stack deploy no son equivalentes: responden a modelos de ejecución distintos.
  • Un stack agrupa servicios, redes y volúmenes como una aplicación desplegable.
  • La sección deploy expresa decisiones de orquestación: réplicas, reinicio, ubicación y actualización.
  • Swarm transforma la especificación declarativa en services, tasks y contenedores distribuidos.
  • Para aplicaciones con imágenes propias, se necesita pensar en registry y disponibilidad de imágenes en todos los nodos.
Resumir conectando con las secciones anteriores: estado deseado, servicios, tareas y redes. Esta es la pieza que permite pasar de comandos manuales a una especificación reproducible.
