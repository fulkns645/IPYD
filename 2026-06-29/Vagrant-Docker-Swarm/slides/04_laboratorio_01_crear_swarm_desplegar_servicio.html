Laboratorio 1

Crear el Swarm y desplegar un servicio

Docker Swarm 04: del comando al estado observable

Objetivo: crear un clúster mínimo, declarar un servicio y observar sus réplicas.

Duración sugerida: 15 minutos | Actividad guiada
Presenta esta sección como el primer contacto práctico con Swarm. La idea no es memorizar comandos, sino ver cómo un comando declara estado y cómo Swarm lo materializa.

Qué debe pasar en este laboratorio

1

Inicializar

Convertir el nodo actual en el primer manager del Swarm.

2

Desplegar

Crear un servicio HTTP simple usando una imagen pública.

3

Observar

Ver el servicio, sus tasks y los contenedores que lo ejecutan.

Idea clave: no vamos a “levantar un contenedor”; vamos a declarar un servicio que Swarm debe mantener activo.

Marca la diferencia con Docker run. Aquí el estudiante está empezando a usar un objeto del orquestador: el service.

Prerrequisitos rápidos

Entorno
  • Docker Engine instalado.
  • Usuario con permiso para ejecutar Docker.
  • Acceso a terminal en el nodo manager.
  • Imagen nginx disponible o acceso a Internet para descargarla.
Escenario mínimo
  • Una máquina basta para comenzar.
  • Ideal: un manager y dos workers.
  • Si hay varias interfaces de red, puede ser necesario usar --advertise-addr.
  • Los comandos iniciales se ejecutan en el manager.
Aclara que se puede hacer un primer laboratorio con un solo nodo. En ambientes con Vagrant o sala de cómputo se puede extender a multinodo.

Paso 1: inicializar el Swarm

manager$
docker swarm init

Resultado esperado

El nodo actual queda como manager y Swarm entrega un comando docker swarm join para agregar workers.

Cuando hay varias IP

docker swarm init \
  --advertise-addr 192.168.56.10
Explica que advertise-addr indica la dirección que otros nodos usarán para contactar al manager. Esto es común en Vagrant, laboratorios y equipos con WiFi/Ethernet.

Paso 2: inspeccionar los nodos

manager$
docker node ls

Lectura de la salida:

STATUS

Indica si el nodo está disponible para el clúster. Ejemplo: Ready.

AVAILABILITY

Indica si el nodo puede recibir tasks. Ejemplo: Active.

MANAGER STATUS

Indica si el nodo participa en el plano de control. Ejemplo: Leader.

La lectura de docker node ls ayuda a conectar el comando con la arquitectura vista en la sección anterior: manager, worker y líder.

Paso 3: crear un servicio web

manager$
docker service create \
  --name web \
  -p 8080:80 \
  nginx:alpine
Solicitud

Crear servicio web

Imagen

nginx:alpine

Puerto

8080 → 80

Explica que -p 8080:80 publica el servicio para poder acceder desde el host o desde el clúster, dependiendo del escenario.

Paso 4: observar servicio, task y contenedor

Servicio
docker service ls

Muestra el servicio, modo, réplicas, imagen y puertos.

Tasks
docker service ps web

Muestra las tasks y el nodo donde fueron ubicadas.

Contenedor real
docker container ls

En el nodo donde corre la task, debe aparecer un contenedor asociado al servicio.

Esta diapositiva es clave. El estudiante debe diferenciar el objeto lógico service, la task asignada por Swarm y el contenedor que realmente corre.

Paso 5: escalar el servicio

manager$
docker service scale web=3

docker service ls
docker service ps web

1

service

3

tasks deseadas

3

contenedores esperados

Conecta explícitamente con estado deseado: ahora el estado deseado del servicio web es 3 réplicas. Swarm debe materializar ese estado.

Paso 6: validar acceso al servicio

Desde navegador
http://IP_DEL_MANAGER:8080

Debe aparecer la página de bienvenida de Nginx.

Desde terminal
curl http://localhost:8080
curl http://IP_DEL_NODO:8080

La validación ayuda a observar la publicación del puerto.

Pregunta guía: si hay 3 réplicas, ¿estamos accediendo a un contenedor específico o a un servicio publicado?

Deja planteado el concepto de servicio publicado antes de entrar más adelante al routing mesh. No profundizar demasiado aquí.

Checklist del laboratorio

  • El nodo actual quedó inicializado como manager.
  • docker node ls muestra el estado del clúster.
  • El servicio web fue creado con una imagen Nginx.
  • docker service ls muestra el número de réplicas.
  • docker service ps web muestra las tasks y su ubicación.
  • El servicio fue escalado a 3 réplicas.
  • El puerto 8080 permite acceder al servicio.
Úsala para cerrar el laboratorio y verificar que todos llegaron al mismo punto antes de pasar a la siguiente sección.

Preguntas para discusión

  • ¿Qué diferencia hay entre ejecutar docker run nginx y crear un servicio con docker service create?
  • Cuando escalamos web=3, ¿qué objeto estamos escalando realmente?
  • ¿Por qué docker service ps web muestra información diferente a docker container ls?
  • ¿Qué significa que el servicio tenga un estado deseado de 3 réplicas?
  • Si una task queda en estado fallido, ¿qué esperaríamos que hiciera el orquestador?
Estas preguntas pueden convertirse después en preguntas tipo Kahoot. Sirven para revisar comprensión conceptual antes de continuar con resiliencia y fallos.
