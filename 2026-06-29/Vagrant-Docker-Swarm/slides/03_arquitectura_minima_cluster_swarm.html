Esta sección conecta el modelo conceptual anterior con la arquitectura real de ejecución: nodos manager, workers, plano de control y plano de ejecución.

Objetivo de esta parte

Comprender la arquitectura mínima que permite que Docker Swarm funcione como un orquestador distribuido.

1

Identificar el rol de los nodos manager y worker.

2

Distinguir entre plano de control y plano de ejecución.

3

Reconocer por qué Swarm necesita consenso entre managers.

El objetivo no es explicar Raft formalmente, sino dar una intuición suficiente para entender por qué varios managers requieren acuerdo.

Dos planos: control y ejecución

Plano de control

Decide qué debe pasar

  • Mantiene el estado del clúster.
  • Recibe órdenes del usuario.
  • Programa tareas en nodos disponibles.
  • Reconcilia estado real vs. estado deseado.
Plano de ejecución

Ejecuta lo que fue asignado

  • Descarga imágenes.
  • Crea y ejecuta contenedores.
  • Reporta el estado de las tareas.
  • Corre la carga real de la aplicación.
Esta separación es clásica en sistemas distribuidos y en sistemas operativos: una parte decide, otra ejecuta.

Arquitectura mínima

Manager

Coordina el clúster y mantiene el estado deseado.

Worker 01

Ejecuta tasks asignadas como contenedores.

Worker 02

Aumenta capacidad y tolerancia a fallos.

Idea clave: un Swarm puede iniciar con un solo manager, pero el valor de la orquestación aparece cuando hay múltiples nodos donde ubicar tareas.

Este diagrama representa un clúster didáctico mínimo: un manager y dos workers. En producción se suelen tener varios managers para alta disponibilidad.

Inicialización y unión de nodos

Manager
# Inicializa el Swarm
$ docker swarm init \
  --advertise-addr 192.168.56.10

# Entrega el token para unir workers
$ docker swarm join-token worker
Worker
# El worker se une al clúster
$ docker swarm join \
  --token SWMTKN-1-... \
  192.168.56.10:2377

# Verificar nodos desde el manager
$ docker node ls

Advertencia didáctica: el parámetro --advertise-addr importa cuando el equipo tiene varias interfaces de red, como suele ocurrir en Vagrant, VirtualBox, WSL o redes de laboratorio.

En laboratorios con máquinas virtuales, --advertise-addr evita que Docker escoja una interfaz incorrecta. Esto reduce errores de conectividad entre nodos.

¿Qué hace un Manager?

Responsabilidades

  • Recibe comandos del cliente Docker.
  • Crea o actualiza objetos: services, networks, secrets, configs.
  • Programa tasks en nodos disponibles.
  • Observa fallos y activa reconciliación.

Desde sistemas operativos

  • Funciona como un scheduler distribuido.
  • Administra recursos del clúster.
  • Mantiene metadata y estado global.
  • Coordina la ejecución de procesos distribuidos.
Relaciona el rol del manager con conceptos vistos en sistemas operativos: planificación, estado, procesos, recursos y recuperación.

¿Qué hace un Worker?

Ejecuta

Corre contenedores asociados a las tasks asignadas.

Reporta

Informa al manager el estado de las tasks y contenedores.

Participa

Se integra a redes overlay y ejecuta la carga real del servicio.

Punto importante: un manager también puede ejecutar tareas como worker, pero en ambientes productivos puede reservarse el manager solo para control.

En una práctica pequeña se puede permitir que el manager ejecute contenedores. En producción, esto puede separarse para proteger el plano de control.

¿Por qué aparece Raft?

¿Cuál es el estado válido del clúster?

Estado

Servicios, redes, nodos, tareas, réplicas y configuración.

Consenso

Los managers acuerdan cambios antes de aceptarlos como válidos.

Líder

Un manager actúa como líder para coordinar las decisiones.

Quórum: intuición práctica

1 manager

Simple

Fácil para prácticas, pero sin alta disponibilidad del plano de control.

3 managers

Recomendable

Puede tolerar la pérdida de 1 manager y mantener mayoría.

5 managers

Mayor tolerancia

Puede tolerar la pérdida de 2 managers, con más costo de coordinación.

Regla intuitiva: para tomar decisiones, los managers necesitan mayoría. Por eso se prefieren números impares de managers.

Puedes presentar la fórmula de tolerancia como floor((N-1)/2), pero enfatizar más la idea de mayoría que la matemática.

Estados de un nodo

$ docker node ls
ID HOSTNAME STATUS AVAILABILITY MANAGER STATUS
ab12 * manager Ready Active Leader
cd34 worker-01 Ready Active
ef56 worker-02 Ready Active
Status

Ready indica que el nodo está disponible para el clúster.

Availability

Active, Pause o Drain controlan si recibe nuevas tareas.

Manager Status

Leader o Reachable aplica a managers.

Esta diapositiva prepara a los estudiantes para interpretar la salida real durante la práctica. No todos los nodos tendrán manager status.

Fallos: ¿qué se puede recuperar?

Falla de task/contenedor

Swarm puede crear una nueva task para restaurar el número de réplicas del servicio.

Ejemplo: eliminar un contenedor manualmente.

Falla de worker

Las tasks pueden ser reubicadas en otros nodos disponibles, si hay capacidad.

Ejemplo: apagar un nodo worker.

Falla de manager único

El clúster puede seguir ejecutando contenedores, pero el plano de control queda afectado.

Ejemplo: no se pueden tomar nuevas decisiones de orquestación.

Falla sin quórum

Los managers restantes no pueden acordar cambios confiables en el estado del clúster.

Ejemplo: pérdida de mayoría de managers.

Diferenciar entre plano de datos y plano de control: los contenedores pueden seguir corriendo, aunque el control del clúster esté limitado.

Ideas clave

  • Un clúster Swarm separa decisiones de orquestación y ejecución de contenedores.
  • Los managers mantienen el estado del clúster y asignan tareas.
  • Los workers ejecutan las tasks como contenedores reales.
  • Con múltiples managers, Swarm necesita consenso para evitar estados contradictorios.
  • La alta disponibilidad del plano de control requiere quórum; por eso se recomiendan números impares de managers.
Cerrar reforzando que el valor del clúster está en mantener servicios distribuidos y no simplemente en tener varios Docker hosts.
