De Docker Compose a Docker Swarm

Primer contacto con orquestación de contenedores

Servicios, réplicas, estado deseado y ejecución distribuida

Duración sugerida: 10 minutos | Bloque 1 de la sesión Swarm
Abrir la sesión conectando con lo que ya conocen: contenedores, redes, volúmenes y docker compose. La pregunta central: ¿qué problema aparece cuando queremos operar varios contenedores en más de una máquina?

Lo que ya resolvimos con Docker Compose

Compose

Aplicaciones multi-contenedor

  • Declaramos servicios en un archivo YAML.
  • Levantamos contenedores, redes y volúmenes con un comando.
  • Facilitamos laboratorios reproducibles y ambientes de desarrollo.
Ejemplo mental

Una aplicación en un host

services:
  web:
    image: nginx
    ports:
      - "8080:80"
  db:
    image: postgres:14
Reforzar que Compose no es obsoleto. Compose es excelente para desarrollo, laboratorios, pruebas locales y despliegues sencillos de un solo nodo.

El límite: una sola máquina

Fallo

Si el host cae, caen todos los contenedores que dependen de él.

Escala

Escalar en una sola máquina queda limitado por CPU, memoria, disco y red del host.

Operación

El ciclo de vida de contenedores distribuidos exige coordinación entre nodos.

Pregunta clave: ¿cómo mantenemos una aplicación viva, escalable y accesible cuando ya no cabe en un solo host?

Aquí aparece la necesidad de orquestación. No presentar Swarm como moda, sino como respuesta a un problema operativo concreto.

Entonces aparece la orquestación

Orquestar significa pasar de administrar contenedores aislados a declarar el estado esperado de servicios distribuidos.

Antes

Contenedores

Crear, detener, borrar y conectar contenedores explícitamente.

Ahora

Servicios

Declarar cuántas réplicas deben existir y dejar que el orquestador actúe.

Enfatizar la transición de imperativo a declarativo. El usuario declara el estado deseado, no cada contenedor individual.

Estado deseado

La idea central

El usuario declara lo que quiere: por ejemplo, un servicio web con tres réplicas. Swarm compara continuamente ese estado deseado con el estado real.

docker service create \
  --name web \
  --replicas 3 \
  -p 8080:80 \
  nginx

Lectura correcta: “quiero que el clúster mantenga tres instancias disponibles del servicio web”.

Si un contenedor muere, Swarm no intenta preservar ese contenedor como individuo. Intenta restaurar el número de réplicas del servicio.

Compose vs. Swarm

Docker Compose
  • Orientado a una máquina.
  • Excelente para desarrollo y laboratorios.
  • Levanta servicios definidos en YAML.
  • No coordina por sí solo un clúster multi-nodo.
Docker Swarm
  • Convierte varios hosts Docker en un clúster.
  • Introduce servicios, tasks y réplicas.
  • Mantiene estado deseado.
  • Permite redes overlay y publicación distribuida de servicios.
Evitar presentar Compose y Swarm como enemigos. Swarm usa archivos tipo Compose mediante docker stack deploy, pero el modelo de ejecución cambia.

Cambio de vocabulario

Service

Declaración lógica: imagen, réplicas, puertos, red y políticas.

Task

Unidad de trabajo que Swarm asigna a un nodo concreto.

Container

Proceso real que ejecuta la task en el host asignado.

Idea clave: en Swarm no pensamos primero en contenedores individuales; pensamos en servicios y réplicas.

Esta diapositiva prepara la práctica posterior: docker service ls, docker service ps y docker container ls muestran niveles diferentes del sistema.

¿Qué agrega Swarm al modelo?

Clúster

Varios nodos Docker coordinados como una unidad lógica.

Scheduling

Asignación de tasks a nodos disponibles según el estado del clúster.

Reconciliación

Corrección automática cuando el estado real se aleja del estado deseado.

Routing

Acceso al servicio publicado sin depender de conocer la réplica exacta.

Overlay

Redes virtuales para comunicación entre servicios ubicados en hosts distintos.

Stack

Despliegue declarativo de múltiples servicios, redes y volúmenes.

Mini-ruta de la práctica

# 1. Crear el cluster
$ docker swarm init

# 2. Crear un servicio
$ docker service create --name web -p 8080:80 nginx

# 3. Escalar el servicio
$ docker service scale web=3

# 4. Observar servicios y tasks
$ docker service ls
$ docker service ps web

Takeaways

Lo que te llevas
  • Compose simplifica apps multi-contenedor, pero asume un solo host.
  • Al crecer, el problema cambia: fallos, escala y coordinación entre nodos.
  • La orquestación es un cambio de enfoque: de administrar contenedores a declarar servicios.
Swarm en una frase
  • Unifica varios hosts en un clúster y aplica scheduling de tasks.
  • Mantiene el estado deseado (ej: réplicas) mediante reconciliación automática.
  • Habilita ejecución distribuida con overlay, routing y despliegue por stack.

Idea clave: en Swarm pensamos primero en servicios y réplicas, no en contenedores individuales.

Slide de cierre del bloque: reforzar el cambio imperativo -> declarativo y el objetivo operacional (mantener servicios vivos y escalables en varios nodos).
