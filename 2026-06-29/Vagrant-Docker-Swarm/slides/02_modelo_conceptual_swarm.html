Docker Swarm

Modelo Conceptual de Swarm

Nodos, servicios, tareas y estado deseado

Sistemas Operativos y Servicios de Red | Posgrado

Parte 02 | Duración sugerida: 15 minutos
Esta segunda parte busca construir el vocabulario mínimo de Swarm. La clave es que el estudiante distinga entre contenedor, task y service, y que entienda el concepto de estado deseado.

La idea central

En Docker Swarm no pensamos primero en contenedores individuales.

Pensamos en servicios que el clúster debe mantener ejecutándose con un estado deseado.

Antes

“Ejecute este contenedor en esta máquina.”

docker run nginx
Ahora

“Mantenga este servicio con N réplicas en el clúster.”

docker service create --replicas 3 nginx
El cambio de mentalidad es fundamental. Docker run crea un contenedor. Docker service create declara un servicio y un estado deseado. Swarm se encarga de materializar ese deseo en tasks y contenedores.

Vocabulario mínimo

Swarm

Clúster de nodos Docker que operan como una unidad lógica.

Node

Máquina física o virtual que participa en el clúster.

Manager

Nodo que administra el estado, agenda tareas y coordina el clúster.

Worker

Nodo que ejecuta las tareas asignadas por el manager.

Service

Definición lógica de lo que debe estar corriendo.

Task

Unidad de ejecución que Swarm asigna a un nodo.

No intentar cubrir todo Swarm aquí. Este vocabulario es suficiente para entender los comandos posteriores: node ls, service ls, service ps, stack deploy.

Service → Task → Container

Service

Declaración lógica: imagen, réplicas, puertos, red, política.

Task

Unidad que Swarm programa en un nodo específico.

Container

Proceso real que ejecuta la imagen solicitada.

docker service create --name web --replicas 3 nginx

Swarm interpreta: “el servicio web debe tener tres tareas activas; cada tarea se ejecutará como un contenedor basado en nginx”.

Esta es quizá la diapositiva más importante de la sección. Reforzar que una task no es exactamente lo mismo que un contenedor: la task es el objeto de orquestación, el contenedor es su ejecución concreta.

Service → Task → Container (2)

Usar la figura para contrastar claramente: escalar verticalmente (una máquina más grande) frente a escalar horizontalmente (varios workers EC2 coordinados). Conectar explícitamente que Dask + EC2 se alinean con el escalado horizontal.

Estado deseado vs. estado real

Estado deseado

Lo que el usuario declara que debe existir.

docker service scale web=5

“Quiero 5 réplicas activas del servicio web.”

Estado real

Lo que realmente está ocurriendo en los nodos.

docker service ps web

“¿Cuántas tasks están corriendo y en qué nodos?”

Orquestar es comparar continuamente ambos estados y actuar para reducir la diferencia.
Esta idea conecta con sistemas operativos: planificación, supervisión, recuperación y reconciliación. Swarm actúa como controlador que intenta acercar el estado real al estado deseado.

El ciclo de reconciliación

1

Declarar estado

2

Observar clúster

3

Detectar diferencia

4

Crear, mover o reiniciar tasks

# Ejemplo de diferencia provocada manualmente

docker container rm -f <container_id>
docker service ps web
Al eliminar un contenedor, el estado real queda por debajo del estado deseado. Swarm no intenta revivir exactamente el mismo contenedor: crea una nueva task para recuperar el número de réplicas solicitado.

Manager y Worker

Manager
  • Mantiene el estado del Swarm.
  • Recibe comandos de administración.
  • Decide dónde ubicar las tasks.
  • Coordina cambios del clúster.
Worker
  • Recibe tasks asignadas.
  • Ejecuta contenedores.
  • Reporta estado al manager.
  • No toma decisiones globales del clúster.

En ambientes pequeños, un manager puede ejecutar contenedores; en ambientes más estrictos se puede separar plano de control y plano de ejecución.

Relacionar con sistemas operativos: un manager se parece al componente que toma decisiones globales; el worker ejecuta la carga. También conviene mencionar que la separación no es absoluta en todos los escenarios.

Comandos para observar el modelo

Nodos
docker node ls

Muestra los nodos del clúster, su rol y disponibilidad.

Servicios
docker service ls

Muestra los servicios declarados y el número de réplicas.

Tasks
docker service ps web

Muestra las tasks del servicio y el nodo donde corren.

Contenedores
docker container ls

Muestra los contenedores reales ejecutándose en el nodo actual.

Reforzar que docker container ls solo muestra los contenedores del nodo donde estoy conectado. Para observar el servicio distribuido se usa docker service ps.

Ejemplo mental

docker service create --name api --replicas 4 mi-api:v1
api.1

worker-01
container A

api.2

worker-02
container B

api.3

worker-03
container C

api.4

worker-01
container D

El servicio es uno: api. Las tasks son varias: api.1, api.2, api.3, api.4. Los contenedores son las ejecuciones concretas en los nodos.

Este ejemplo ayuda a los estudiantes a ver que el nombre del servicio no es el nombre de cada contenedor. También permite explicar que una réplica puede ser reubicada si falla un nodo o un contenedor.

Takeaways

  • Swarm introduce un modelo declarativo basado en servicios.
  • Un service describe qué se quiere ejecutar y con cuántas réplicas.
  • Una task es la unidad que Swarm asigna a un nodo.
  • Un container es la ejecución concreta de una task.
  • El orquestador compara estado deseado y estado real para mantener el sistema operativo.
Cerrar reforzando el vocabulario. Antes de pasar a redes o stacks, estos conceptos deben quedar claros.

Preguntas para discutir

1. ¿Por qué en Swarm es más preciso hablar de “servicios” que de “contenedores”?

2. Si elimino manualmente un contenedor de un servicio con 3 réplicas, ¿qué debería hacer Swarm?

3. ¿Qué diferencia hay entre docker service ps y docker container ls?

4. ¿Qué parte del modelo conceptual se parece más a un scheduler de sistema operativo?

Estas preguntas pueden convertirse luego en preguntas tipo Kahoot. También permiten diagnosticar si el grupo entendió la diferencia service-task-container.
