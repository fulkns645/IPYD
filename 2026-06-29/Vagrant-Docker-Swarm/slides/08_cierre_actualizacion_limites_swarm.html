¿Qué significa actualizar un servicio?

En modo standalone

Pensamos en contenedores

Detener, recrear o reemplazar contenedores individuales. El operador controla explícitamente gran parte del ciclo de vida.

En Swarm

Pensamos en servicios

Se declara una nueva versión del servicio y el orquestador reemplaza gradualmente las tasks para acercarse al nuevo estado deseado.

Idea clave: actualizar no es “entrar al contenedor y cambiarlo”; es declarar una nueva configuración del servicio.

Refuerza el cambio de mentalidad: los contenedores son reemplazables; el service es la abstracción que se administra.

Comandos básicos de cierre

# Crear un servicio web publicado en el puerto 8088
 docker service create \
   --name web \
   -p 8088:80 \
   nginx:1.25

# Escalar horizontalmente el servicio
 docker service scale web=5

# Actualizar la imagen del servicio
 docker service update --image nginx:1.26 web

# Forzar una redistribución de las tasks
 docker service update --force web

Estos comandos permiten cerrar el ciclo: crear, escalar, actualizar y observar cómo Swarm reconcilia el estado del servicio.

Puedes ejecutar estos comandos en vivo o dejarlos como recapitulación. Conviene que los estudiantes predigan qué cambiará antes de ejecutar cada comando.

Rolling update: reemplazo gradual

Paso 1

Servicio actual con varias réplicas.

Paso 2

Swarm detiene algunas tasks y crea nuevas con la imagen actualizada.

Paso 3

El servicio converge hacia la nueva versión.

docker service update \
  --update-parallelism 1 \
  --update-delay 10s \
  --image nginx:1.26 \
  web
Explica parallelism como cuántas tasks se actualizan simultáneamente y delay como pausa entre grupos de actualización.

Escalar no siempre significa lo mismo

Stateless

Fácil de escalar

  • APIs REST
  • Servidores web
  • Workers sin estado local
  • Servicios idempotentes
Stateful

Escalamiento delicado

  • Bases de datos
  • Colas con persistencia
  • Sistemas con archivos locales
  • Servicios con sesiones no externalizadas
Conecta con Drupal + PostgreSQL: Drupal puede escalarse con más facilidad; PostgreSQL requiere pensar en datos, volúmenes, replicación y ubicación.

El límite más importante: los datos

Swarm puede mover o recrear tasks, pero los datos persistentes no se mueven mágicamente con la misma facilidad que un contenedor.

Qué hace bien Swarm y qué no resuelve solo

Fortalezas
  • Orquestación integrada con Docker.
  • Modelo simple de services y replicas.
  • Redes overlay y service discovery.
  • Rolling updates con baja complejidad.
  • Buena puerta de entrada a la orquestación.
Límites
  • Ecosistema menor que Kubernetes.
  • Menos extensibilidad del plano de control.
  • Persistencia distribuida no trivial.
  • Observabilidad y políticas avanzadas requieren integración externa.
  • No elimina la necesidad de diseño operacional.
Evita presentar Swarm como “inferior” o “suficiente para todo”. Es una herramienta con un espacio de uso claro.
