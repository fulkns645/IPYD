Docker Swarm · Sección 06

Redes de servicios:
routing mesh, puertos y overlay networks

Cómo se comunican los servicios dentro y fuera del clúster

Teórico-práctico · 15 minutos
Presenta esta sección como el puente entre servicios distribuidos y servicios de red. Ya no basta saber dónde corre un contenedor; importa cómo se alcanza.

Pregunta guía

Si una réplica de web está corriendo en worker-02, ¿por qué puedo acceder al servicio desde el IP del manager?

Entrada

Puerto publicado

Hace visible un servicio hacia fuera del clúster.

Distribución

Routing mesh

Permite recibir tráfico en cualquier nodo del Swarm.

Comunicación interna

Overlay network

Conecta servicios que pueden estar en distintos hosts.

La pregunta inicial ayuda a romper la asociación ingenua entre puerto publicado y nodo donde vive físicamente el contenedor.

Publicar un puerto

# Servicio HTTP publicado
docker service create \
  --name web \
  --replicas 3 \
  -p 8080:80 \
  nginx
Lectura

-p 8080:80 significa:

  • 8080: puerto visible en el clúster.
  • 80: puerto interno del contenedor.
  • El cliente no necesita saber en qué nodo corre la task.

Idea clave: publicar un puerto expone un servicio, no un contenedor particular.

Conecta este punto con la diferencia entre container port y published port vista en Docker básico, pero ahora aplicada a un servicio.

Routing mesh

Routing mesh: cuando un servicio publica un puerto en modo ingress, cualquier nodo del Swarm puede recibir la conexión y redirigirla hacia una task disponible del servicio.

Aclara que esto es útil para simplificar el acceso externo: el usuario puede llegar por cualquier nodo, aunque la réplica esté en otro.

Mensaje para sistemas operativos y redes: el servicio abstrae un conjunto de procesos distribuidos y Swarm ofrece un punto lógico de entrada para balancear tráfico hacia ellos.

No profundices demasiado en IPVS en esta primera clase. Puedes mencionarlo oralmente como mecanismo de balanceo L4 usado por Swarm.

Overlay networks

# Red virtual distribuida entre nodos
docker network create \
  --driver overlay \
  appnet
Qué resuelve

Permite que servicios ubicados en diferentes hosts se comuniquen como si estuvieran en una misma red lógica.

Cómo se usa

Los servicios se conectan a la red overlay usando --network appnet o mediante un stack.

Contrasta rápidamente bridge network, que es local al host, con overlay network, que cruza hosts dentro del Swarm.

Mini-demo: Drupal + PostgreSQL

# Crear red y servicio de base de datos
docker network create --driver overlay mydrupal

docker service create \
  --name psql \
  --network mydrupal \
  -e POSTGRES_PASSWORD=mypass \
  postgres:14
# Crear servicio web conectado a la misma red
docker service create \
  --name drupal \
  --network mydrupal \
  -p 8080:80 \
  drupal:9
Este ejemplo conecta con la práctica del material base. No es necesario configurar Drupal completo; basta observar servicios, red y publicación de puerto.

Objetivo: no memorizar comandos, sino observar cómo Swarm conecta puertos publicados, redes overlay, servicios y tasks.

Si el grupo trabaja con varios nodos, pídeles identificar en qué nodo está cada task y desde qué nodo pueden acceder al puerto publicado.

Advertencias operativas

Servicios stateless

Más fáciles de escalar

APIs REST, servidores web y frontends suelen funcionar bien con réplicas y balanceo.

Servicios stateful

Requieren más diseño

Bases de datos, colas y almacenamiento persistente necesitan estrategia de volúmenes, ubicación y respaldo.

Escalar Drupal no es lo mismo que escalar PostgreSQL.

Refuerza una idea crítica: Swarm facilita orquestación, pero no elimina los problemas fundamentales de datos persistentes y consistencia.
