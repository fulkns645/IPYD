Observar la recuperación

Swarm detecta que el estado real ya no coincide con el estado deseado y crea una nueva task.

Idea central: Swarm no protege un contenedor específico; mantiene el número de réplicas declarado para el servicio.

Diferencia entre cuidar una instancia concreta y sostener una especificación declarativa.

Reconciliación: proceso mediante el cual el orquestador compara lo que debería existir con lo que realmente existe y ejecuta acciones correctivas.

Explica que esta es una idea común en orquestadores modernos, incluidos Kubernetes y otros sistemas declarativos.

Ubicar los contenedores reales

Asegúrate de que todos tengan un servicio con al menos tres réplicas antes de provocar la falla.

Identificar el contenedor asociado

# Ver tasks del servicio
docker service ps web
# Ver contenedores locales
docker container ls

Los nombres suelen tener una forma similar a:

web.1.xxxxxxxxxxxx
web.2.yyyyyyyyyyyy
web.3.zzzzzzzzzzzz
Aclara que en un clúster multinodo cada estudiante podría no ver todos los contenedores con docker container ls si está conectado a un solo nodo.

Provocar la falla

# Eliminar una réplica manualmente
docker container rm -f <container_id_o_nombre>

Pregunta inmediata: ¿acabamos de reducir el servicio de 3 a 2 réplicas, o solo destruimos un contenedor que Swarm considera reemplazable?

contenedor eliminado breve inconsistencia reconciliación
Es importante no usar docker service scale aquí; queremos una falla accidental, no un cambio declarativo.

Observar la reconciliación

# Verificar estado del servicio
docker service ls

docker service ps web

docker container ls
Lo que veremos

Una task queda marcada como fallida, apagada o removida.

Lo importante

Swarm crea otra task para volver al número de réplicas esperado.

Enfatiza que service ps conserva historia de tareas: no solo muestra las vivas, también permite interpretar eventos recientes.

Falla vs. cambio intencional

Falla
docker container rm -f <id>

El estado deseado no cambia. Swarm reemplaza la réplica perdida.

Cambio declarativo
docker service scale web=2

El estado deseado sí cambia. Swarm reduce el servicio a dos réplicas.

En Swarm, el camino correcto para modificar una aplicación es cambiar el service, no manipular contenedores individuales.

Esta diapositiva ayuda a que no confundan intervención manual con operación declarativa.

Lectura operativa del evento

1

El usuario declara 3 réplicas.

2

Una réplica desaparece.

3

4
